## 1. 리더와 워커의 역할
에이전트 여럿을 쓸 때의 기본은 리더가 직접 하는 것임. 워커는 지시서와 코드를 읽고 환경을 맞추는 비용이 실제 일보다 큰 경우가 많고, 에이전트 하나는 대화보다 약 4배, 여러 에이전트는 약 15배의 토큰을 쓰기 때문임(Anthropic 2025). 그래서 워커는 연구자가 요청하거나 워커로 일하기로 정했을 때만 쓰고(사용량 한도 때문에 맡기기로 한 경우 포함, 5장), 그 안에서도 따로 떼어 낼 결과물(모듈과 그 시험, 측정 도구)이 있는 일에만 띄움. 워커는 만들고 띄우는 데서 끝나고, 기다리고 판정하는 일은 리더가 맡음.

### 1.1 누가 하는가
리더는 사전 측정 스크립트, 몇 줄 고치기, 기록, 판정, 짧은 문서 작업을 직접 함. 워커는 코드만 쓰고 실행하지 않은 채 멈추기도 하므로, 에이전트를 늘리기 전에 리더 혼자나 스크립트 한 번으로 되는지 먼저 봄.

워커의 일은 아래 다섯 단계에서 끝남. 지켜보기만 하는 워커는 두지 않음.
1. **작성**: 코드·시험·설정을 만듦.
2. **검증**: 줄인 출력이 아니라 시험 자체의 종료 상태로 통과를 확인함.
3. **실행**: 작업을 띄움.
4. **시작 확인**: 첫 로그 줄이나 프로세스로 시작을 확인함.
5. **반납**: 실행 위치·PID·시작 시각·예상 끝·확인할 지점(smoke, 접기 판정, 끝)을 인계 기록에 남기고 칸을 닫음.

기다리기와 판정은 리더가 함. 연구자는 에이전트 없는 모니터 칸(4장)으로 진행을 보고, 리더는 확인할 지점마다 한 번씩만 깨어남. 에이전트는 마지막 감시 하나만 두고, 커밋한 뒤에는 멈춤.
- 한 워커에는 한 질문·한 파일 범위만 맡기고, 여러 결과를 하나로 종합하는 일은 리더가 함.
- 조사는 좁은 질문 여러 개로 나눠 조사 에이전트를 병렬로 띄우고, 본문 확인 수준을 표시하게 함.
- 작은 변경을 누가 맡을지 지시가 엇갈리면 연구자에게 한 번 묻고, 답을 운영 문서에 적음.
- 검증·자문 워커와 실행 워커는 다른 모델 계열을 써서 검증의 독립성을 지킴. 모델 이름은 코드에 박지 않고 설정으로 고름.
- 워커의 추론 수준(effort)은 일에 맞는 최소로 두고, 가장 높은 수준은 정말 어려운 일에만 씀. 실행 중인 워커의 모델·추론 수준은 바꾸지 않음.
- 사용 한도에 걸리면 미리 정해 둔 저가·무료 경로로 바꿈.

### 1.2 워커 지시서
지시서는 워커가 다른 문서 없이 일을 끝낼 수 있게 씀. 지시서가 모호하면 워커끼리 일이 겹치거나 빈틈이 생기고, 막힌 워커는 스스로 우회로를 찾다가 연구자의 작업 환경을 바꿀 수 있음. 지시서에는 아래를 모두 담음.

| 항목 | 쓰는 법 |
| --- | --- |
| 목표와 경계 | 목표, 결과물 형식, 쓸 도구와 출처, 하지 말 경계를 적음 |
| 경로·장비·모델 | 다른 지시서를 참조하지 않고("다른 지시서와 같음" 금지) 그 안에 모두 적음. 경로는 절대 경로로 주어 실수하기 어렵게 함 |
| 장비 값 | 메모리 한도·GPU 수는 실제로 확인한 값을 적음. 추측한 값은 배치 줄이기·멈춤 같은 잘못된 판단으로 이끔 |
| 비교 모델 | 측정·비교에 쓰는 모델은 기본으로 채택된 바탕 줄이고, 다른 줄을 쓰면 이유를 적음 |
| 끝 표시 | 마지막 단계에 "인계 기록을 남기고 작업을 완료로 표시"를 적음. 없으면 리더의 대기가 깨어나지 않아, 끝난 일이 멈춘 것처럼 보임 |
| 긴 실행 | 시작 확인 직후 인계하게 하고, 첫 epoch나 끝까지 기다리게 하지 않음. 학습 뒤 채점·측정은 서버에서 학습과 한 스크립트로 묶어(학습 → 채점 → 측정 → 끝 표시) 한 번에 띄움. 실행기가 학습 전에 smoke를 돌리면 같은 smoke를 따로 돌리지 않음 |
| 환경 | 맡긴 범위 밖의 작업 환경(접속·인증 설정, 시스템 설치, 다른 실험의 파일, 열린 앱)을 바꾸지 않음. 서버나 외부 자원에 닿지 않으면 고치려 하지 말고 멈춰서 보고함 |
| 질문 | 질문 창을 띄우지 않고, 모르면 안전한 기본값을 쓰고 인계 기록에 적음 |
| 권한 | 도구와 권한은 맡긴 일에 필요한 만큼만 줌. 메시지 보내기, 삭제, push처럼 되돌리기 어려운 일은 리더나 연구자가 함 |
- 리더는 워커를 띄우기 전에 지시서에 "끝날 때까지 기다림" 단계가 없는지 확인함.

### 1.3 띄운 뒤
완료 표시는 마지막 확인일 뿐이고, 워커의 결과는 리더가 따로 검증함. 역할을 잘 적어 주어도 다중 에이전트의 실패는 일부만 줄기 때문임(Cemri 외 2025). 진행 상황은 연구자가 묻기 전에 리더가 알고 있어야 함.
- 띄운 직후부터 워커가 실제로 하는 일(실행 중인 프로세스, 로그, 원격 장비의 GPU·파일)을 직접 들여다봄. 지시서·설계 문서에서 벗어난 일(예: 계획에 없던 재계산)이 보이면 그 자리에서 맞는지 판단해 설계 문서에 보충·정정으로 기록함.
- 워커가 쓴 코드는 설계 문서와 한 줄씩 대조해 검토하고, 시험·smoke·학습은 리더가 직접 돌림. "시험 통과" 보고만으로 학습하지 않고, 시험이 겨냥한 성질을 실제로 가르는지도 봄(예: 같은 seed로 만든 두 모델을 비교하는 시험은 거의 늘 통과함).
- 워커가 띄운 뒤 결함을 찾으면 혼자 다시 띄우지 않음. 자기가 띄운 PID만 멈추고, 실행 폴더는 지우지 않고 실패로 표시해 남기고, 결함과 고친 내용을 인계 기록에 적어 리더에게 넘김. 다시 띄우기는 지시서가 허락할 때만 함.
- 워커 칸은 그 워커가 끝났는지(칸 출력, 서버 프로세스) 확인한 뒤 닫음. 강제로 닫는 명령은 끝난 것이 확인된 워커에만 씀.

### 1.4 병렬과 합치기
서로 독립인 일은 동시에 돌려 결정에서 결과까지의 시간을 줄이고, 합치기는 리더 한 사람이 맡음. 여럿이 같은 것을 고치면 합칠 때 충돌하거나 승인된 문장이 잘려 나가기 때문임.
- 서로 독립인 단계는 GPU를 나눠 동시에 돌림. 통과선이 없는 사전 측정은 학습을 막지 않으며, 학습을 먼저 띄우고 측정은 다른 GPU에서 함께 돌려 해가 나오면 그때 학습을 멈춤.
- 워커는 따로 떨어진 작업 공간(worktree)에서 커밋만 하고, 합치기와 충돌 해결은 리더가 함. 작업 줄이 옛 main에서 갈라졌으면 main 구조 위에 작업 줄의 값만 옮김. 워커를 띄우는 순간에는 리더가 커밋하지 않음(기준 커밋이 바뀌면 작업 공간 만들기가 실패함).
- 한 원고의 서로 다른 절은 여러 워커가 병렬로 고침. 워커마다 겹치지 않는 문단 범위와 지우면 안 되는 승인 문장 목록을 주고, 빌드 산출물은 커밋하지 않게 하며, 분량은 맞추지 말고 늘어난 줄 수만 보고하게 함. 리더가 합친 뒤 한 번만 빌드해 분량을 원고 전체에서 맞춤.
- 다중 에이전트 도구의 성능은 메시지 수나 확인 응답 수가 아니라 완료한 과업당 비용과 결과의 질로 판단함. 평가자가 과업 정보를 미리 보면 그 평가는 무효임. 같은 접두 문맥을 재사용하고 도구 출력을 줄이면 비용이 크게 줄어듦.

## 2. 긴 작업 규칙
10분이 넘을 수 있는 작업(전처리, 평가, 사전 측정)을 돌릴 때 지시서에 그대로 붙이는 규칙임. 핵심은 띄우기 전에 시간을 재고, 돌기 시작하면 한 번만 확인하고, 띄운 사람은 기다리지 않는 것임.

1. **먼저 추정함.** smoke에서 표본당 시간을 모델 계산·CPU 작업·채점으로 나눠 재고, 전체 예상 시간을 보고함. 45분이 넘으면 병목과 고친 방법을 적음. 모델 준비 같은 시작 비용은 표본당 시간에서 빼고 추정함.
2. **비어 있는 CPU 코어를 처음부터 씀.** 표본별 CPU 작업은 데이터 로더 worker나 프로세스 풀에서, 무거운 채점은 GPU에서 함. 계산은 빠른데 한 코어에서 채점하느라 전체가 몇 배 느려지는 일이 흔함.
3. **처리 속도를 한 번 점검함.** 전체의 약 5%가 지난 뒤 GPU 사용률과 가장 바쁜 코어를 잼. GPU가 놀고 한 코어만 바쁘면 멈추고 고쳐 다시 돌림. 다만 스크립트가 이 점검으로 스스로 멈추게 하지 않고 숫자만 보고함. 공유 저장소에서 읽는 시간이 병목인 작업은 GPU 사용률이 원래 낮음.
4. **중간 결과를 저장함.** 일정 간격으로 저장하고 이어서 돌 수 있게 함. 출력 단계는 저장된 값만 읽게 해, 마지막 단계에서 죽어도 몇 초 만에 다시 냄.
5. **smoke는 모든 분기를 지나게 함.** 실제 출력 단계까지 돌고, 데이터에 따라 갈리는 모든 분기를 한 번씩 지나게 함. smoke가 지나지 않은 분기는 긴 실행의 마지막에서 터질 수 있음.
6. **실제 시간을 함께 적음.** 보고에는 추정 시간 옆에 실제 시간을 적음.
7. **띄우면 바로 인계함.** 작업을 띄운 뒤 기다리지 않음. 프로세스 번호, 로그 위치, 출력 위치, 예상 종료 시각을 넘기고 끝냄. 기다리기는 리더의 감시 하나가 맡고, 긴 sleep을 한 번에 걸지 않음. 긴 sleep은 결과를 늦게 알아채게 함.

## 3. 서버와 GPU
에이전트는 노트북에서, 계산은 원격 서버에서 하는 구조를 전제로 함. 지킬 것은 셋임. 작업은 접속과 분리해 띄우고 번호로만 다루며, 남의 자원과 환경은 건드리지 않고, GPU는 쉬지 않게 채우되 무엇을 접을지는 결과 전에 정함.

### 3.1 띄우고 멈추기
- 긴 작업은 셸과 분리해 띄움(`setsid nohup … &`). 그냥 백그라운드로 띄우면 접속이 끊길 때 함께 죽음. 실행 권한이 없는 스크립트는 `bash`를 앞에 붙임.
- 띄우는 순서와 명령, 실행기의 인자 형식을 운영 문서에 그대로 등록해 매번 다시 헷갈리지 않게 함.
- 학습을 띄울 때마다 실행 문서 한 장을 씀: 무엇을 실행하나(줄·설정·커밋·스크립트·GPU·seed·상태 기록·감시), 어떤 방법론인가(쉬운 말과 분야 용어, 바탕 대비 바꾼 것), 앞서 무엇을 쟀나(전제 측정·관련 결과 문서로 이어 주고 핵심 숫자와 판정), 판정 기준과 갈림길, 끝나면 결과 문서. 설계·결과 문서와 서로 가리키게 하고, 이후 논의는 이 문서를 기준으로 함.
- 띄운 뒤에는 대기열 기록의 시작 줄을 확인하고, 실제 학습 시작 줄을 본 뒤에만 "학습 시작"으로 보고함.
- 프로세스는 번호로만 멈춤. 이름 패턴으로 죽이면 명령 자신이나 남의 작업이 함께 죽음.
- 원격 셸의 환경이 다르면(예: 가상환경이 켜지지 않음) 실행 파일 경로를 명시함. 긴 대화형 작업은 터미널 다중화 도구 안에서 돌림.
- 위험한 스크립트는 인자·필수 변수가 없으면 먼저 멈추게 둠. 셸로 파일을 쓰는 요령처럼 도구에 묶인 규칙은 방법 문서가 아니라 전역 지침에 둠(설치 안내 1.4).

### 3.2 공유 자원과 환경
- 다른 사람이 쓰는 GPU는 쓰지 않음. 허락받은 GPU만, 정해진 시간대에만 씀. 시간 제한이 있는 GPU는 실행기가 시간 밖 시작을 거부하고, 마감 전에 끝나도록 함.
- 공유 저장소의 응답이 느려지는 시간대에는 새 작업을 시작하지 않고, 그 시간대의 시험 실패를 코드 탓으로 보지 않음. 예외 스위치를 둬 연구자가 허락하면 건너뜀.
- 새 도구를 설치하기 전에 이미 서버나 공유 저장소에 있는지 확인하고, 설치는 개인 가상환경에만 함.
- 큰 원본은 스트리밍으로 읽고 필요한 결과(예: 임베딩)만 남김.

### 3.3 GPU를 쉬지 않게 채우기
한 줄이 도는 동안 다음 줄의 설계·코드·시험을 끝내 두고, 끝나거나 접히면 바로 띄움. 확인용 학습이 GPU 하나로 되고 빈 GPU가 있으면, 판정 기준을 등록한 뒤 관련 없는 작업이 끝나기를 기다리지 않고 바로 띄움.
- 다음 입력은 CPU가 미리 준비함.
- GPU를 다 못 쓰는 작은 작업은 메모리가 남는 GPU에 두 번째 자리로 넣음. 학습은 두 번째 자리에 넣지 않음(학습 하나가 GPU를 거의 다 쓰면 둘을 함께 올려도 처리량이 늘지 않고 결과만 늦게 나옴). 학습 줄이 GPU보다 많으면 남는 줄은 먼저 끝나는 GPU 뒤에 차례로 이어 붙임. 처음 돌리는 종류의 작은 작업은 혼자 돌려 최대 메모리를 잰 뒤에 넣음. 올린 뒤 GPU 사용률을 몇 번 재고, 두 작업이 함께 도는 GPU는 실행 원장에서 메모리 부족 실패가 없는지 확인함. 실패가 있으면 그 종류는 두 번째 자리에서 뺌.
- GPU 하나를 다 쓰지 않는 실행 여럿을 한 GPU에 올릴 때는, 실행당 최대 메모리를 같은 설정의 smoke(epoch 끝의 평가·저장 구간 포함)에서 재고, 합이 GPU 용량에 여유를 남기는 선을 넘으면 하나 줄여 띄움. 띄운 직후 사용량이 그 선을 넘으면 첫 epoch 끝 전에 줄임. 메모리 꼭대기는 epoch 끝처럼 늦게 와서, 어림으로 띄우면 여러 실행이 한꺼번에 죽고 같은 시점에 돌리려던 조건도 깨지기 때문임.
- 사전 측정은 빈 GPU에서 메모리 상한과 낮은 우선순위로 돌림.
- 중간에 접기: 지난 줄들의 학습 곡선과 최종 판정을 맞대어, 중간에 확실히 잴 수 있는 값으로 "이만큼 뒤처진 줄은 끝까지 가도 통과한 적 없음"인 선을 결과 전에 등록하고, 그 선에 걸리면 접음. 중간 값으로 채택은 하지 않음(앞선 줄이 최종 판정에서 떨어진 예가 있음). 접은 줄도 저장된 checkpoint로 판정 채점을 남김.

### 3.4 백업과 기계 옮기기
- 원자료는 읽기 전용으로 두고 한 부는 다른 장소에 사본으로 둠.
- 서버 공백에 대비해 결과를 백업하고, 백업만 하지 말고 복원 시험도 함. 백업 폴더에 복원 순서를 적어 두고, 이미 다른 저장소에 있는 결과·체크포인트는 다시 복사하지 않음. 비밀 값(API 키, 인증 정보, SSH 키)은 백업에 넣지 않고 새 기계에서 다시 입력함.
- 학습한 모델을 다른 기계나 사본에서 다시 채점할 때는, 실행 전에 가중치 파일이 있는지와 해시를 확인하고, 채점 결과 일부를 저장된 예측과 먼저 대조함. 가중치가 없어도 오류 없이 기반 모델로 도는 채점기가 있어, 조용한 대체가 학습 모델의 결과로 기록될 수 있기 때문임.
- 장비를 반납하거나 다른 기계로 작업을 옮길 때는 결과·그림·문서를 작업할 기계로 먼저 옮기고, 그 기계에서 할 일과 하지 않을 일(예: 학습은 하지 않고 원고만 고침)을 운영 문서에 적고, 설정 파일의 경로(훅 설정 등)를 새 기계 값으로 고침.

## 4. 감시와 모니터
감시는 띄울 때 저장한 pid의 종료로 기다리고, 성공 여부는 로그의 끝 표시 줄로 판단함. 결과 문자열만 기다리면 시작 직후 오류로 끝난 작업을 끝까지 기다리게 되고, 경로가 틀린 감시는 실패하지도 끝나지도 않고 조용히 남아 에이전트가 말없이 멈춘 것처럼 보이기 때문임. 그래서 모든 감시에는 시간 상한을 두고, 사람이 보는 모니터는 에이전트 없이 따로 둠.

감시는 아래 순서로 걺.
1. **시작을 확인함.** 띄우고 수십 초 뒤 로그 첫 줄로 시작을 확인함.
2. **볼 파일을 확인함.** 감시가 볼 파일의 경로와 줄의 꼴은 추측하지 않고, 지난 실행이 남긴 같은 파일에서 실제로 확인함.
3. **pid 종료로 기다림.** 대기 조건은 결과 문자열이 아니라 pid 종료에 걸어 어떤 끝(오류 포함)이든 잡음. 끝 표시 줄(종료 줄, smoke 결과 줄, 첫 epoch 줄)은 이번 실행의 줄만 맞도록 패턴을 정함. 지난 실행의 실패·건너뜀 줄이 남아 있으면 바로 끝난 것으로 오판함.
4. **시간 상한을 둠.** 예상 시각에 여유를 더한 상한을 두고, 상한에 걸리면 서버의 로그·파일을 직접 보고 무엇이 늦는지 연구자에게 바로 알림. 감시가 깨우지 않는다고 해서 아무 일이 없다고 여기지 않음.
5. **함께 멈춤.** 실행을 멈추면 그 실행을 기다리던 감시도 함께 멈춰, 끝나지 않을 감시를 남기지 않음.

- 프로세스 이름 검색은 감시 명령 자신과 일치해 영원히 "실행 중"으로 보일 수 있으므로, 쓰려면 자기와 맞지 않는 꼴(`[s]moke`)로 씀.
- 감시 출력은 grep으로 확인함. 셸마다 단어 분리 규칙이 달라 변수로 나누면 오판하고, 그동안 GPU가 놀 수 있음.
- 긴 로그는 tail로 보지 않고 원격 grep으로 필요한 줄만 뽑음. 줄이 긴 로그는 tail 창이 결과 줄을 놓침.
- 노트북 절전·이동으로 로컬 감시가 끊겼다가 연구자가 물으면, 감시 출력이 아니라 서버의 대기열 기록부터 확인함. 네트워크 설정은 에이전트가 건드리지 않음.
- 지켜보기는 에이전트 워커가 아니라 **에이전트 없는 모니터 칸 하나**로 함. 모든 실행의 epoch·최신 값·끝/오류를 2분마다 한 줄씩 보여 주고, 대화 칸 아래에 한 칸으로 둠. 판정은 리더가 함.
- 모니터에는 진행(몇 번째 epoch)과 함께 연구자가 실제로 판단에 보는 값을 띄우되, 판정 채점과 같은 정의(빼는 칸, 쓰는 체크포인트)인 값만 띄움. 띄우기 전에 저장된 채점값 하나와 맞춰 보고, 정의가 다른 값이면 그 차이를 화면에 적고 바탕 대비 비교 칸은 뺌. 연구자는 화면의 추세를 결과로 읽으므로, 판정과 다른 정의의 값은 방향이 반대인 판단을 부를 수 있기 때문임.

## 5. 보안과 비용
개인정보와 비밀 값은 명령·출력·기록 어디에도 남기지 않고, 돈이 드는 실행은 상한을 두고 미리 셈함. 한 번 새어 나간 값은 되돌릴 수 없고, 상한 없는 실행은 사용량을 순식간에 써 버리기 때문임.
- 사용자 이메일 같은 개인정보를 명령·API 인자·파일에 넣지 않음. 일부 검색 API는 연락처를 요청 인자로 받으므로 조사 에이전트 지시문에 금지 문장을 넣음.
- 비밀 값이 들어 있을 수 있는 줄(예: 옛 로그의 webhook 주소)은 출력하지 않도록 필터를 붙이고, 관련 환경변수는 빈 값으로 실행함.
- VPN·네트워크 설정은 건드리지 않음. 끄라는 지시가 있을 때 정해진 정지 스크립트만 실행함.
- API 키는 사람별 프로파일로 나누고, 기록에는 금액만 남기고 키 값은 남기지 않음. 한 실행에는 키 하나만 씀. 여러 키를 합쳐 한 실행을 나누면 기록과 재시도가 갈라짐.
- 유료 API는 크레딧 만료일을 보고 먼저 쓸 키를 정하고, 실행 전에 실측 단가로 비용을 계산해 잔액 안인지 확인함. 같은 모델·문장으로 이미 실측했으면 파일럿 생략 사유를 사전 등록 문서에 적음.
- 에이전트 실행과 유료 API에는 반복 수·시간·비용 상한을 두고, 상한에 닿으면 멈추고 알림. 사용량이 평소보다 크게 튀면 계속하기 전에 원인을 확인함.
- 사용량 한도 때문에 연구자가 워커로 일하기로 정했을 때만, 실제 작업(코드·측정·실행·결과 가져오기)은 값싼 모델의 워커에게 지시서 파일 하나로 맡기고, 리더는 지시·판정·문서만 함. 답과 도구 출력도 짧게 유지함. 큰 모델의 사용량이 연구 기간 내내 모자라지 않게 하기 위함.

## 6. 커밋과 push
커밋은 의도한 변경만, 되돌릴 수 있는 작은 단위로, 대응하는 문서와 함께 남김. push는 사람이 지시했을 때만 하고, 올리기 전에 아래를 점검함. 기록과 결과가 같은 커밋에 있어야 나중에 어느 결과가 어느 코드에서 나왔는지 추적할 수 있음.
- 의도한 파일만 커밋함. 디렉터리 단위로 추가하지 않고, 남이 고치던 미커밋 파일은 건드리지 않음.
- 커밋은 한 번에 되돌릴 수 있을 만큼 작은 단위로 하고, 끝나지 않은 작업은 커밋하지 않음. 다시 만들 수 있는 중간 파일과 큰 파일은 넣지 않음.
- 코드·원고 변경과 그에 대응하는 문서(설계·결과)는 같은 커밋에 넣고, 연구자에게 보고할 때 어느 문서에 남겼는지 경로를 함께 적음.
- 결과 데이터는 git에 넣지 않고 별도 저장소(예: NAS)에 둠. 원고도 git으로 추적하되 빌드 산출물과 옛 백업은 제외하고, 비공개 저장소일 때만 원고를 push함.
- 사전 등록 문서는 결과 전에 커밋해 시각을 남김. 시각은 짐작하지 않고 시계나 커밋 시각에서 읽음.
- 그림의 이름표만 바꾸는 재생성은 옛 그림과 새 그림을 같은 해상도로 픽셀 비교하고, 이름 외 차이가 있으면 커밋하지 않고 멈춤. 그림과 캡션의 판이 어긋나는 일을 이 비교로 찾을 수 있음.

push는 아래 순서로 함.
1. 사람이 지시했는지 확인함.
2. 비밀 값을 점검함.
3. 문서를 점검함: 변경에 대응하는 계획·결과·설계 문서가 갱신됐는가, 머리말이 있는가, 실패·누락이 기록됐는가, 문서가 가리키는 경로가 실제로 있는가, 남은 작업이 의도된 것인가, 결과 데이터가 커밋에 섞이지 않았는가, 무엇을 왜 올리는지 한 줄 요약이 있는가.
4. 정해진 원격 브랜치에만 올림. 공유 저장소의 다른 브랜치나 main은 건드리지 않음. 연구자 혼자 쓰는 저장소는 작업 브랜치가 main에서 곧게 이어질 때(fast-forward) main에도 올리고, main을 강제로 덮어쓰지 않음.
