# AI 활용 연구 방법 — AI가 틀리는 유형과 대응

| 항목 | 내용 |
| --- | --- |
| 목적 | 이 문서만 보고 AI 에이전트가 연구 중에 반복해서 틀리는 곳을 미리 알아차리고, 틀렸을 때 바로잡고, 다시 틀리지 않게 장치로 옮길 수 있게 함 |
| 읽는 상황 | AI의 답·결과·보고가 이상할 때, 같은 실수가 두 번 나왔을 때, 결과를 판정하거나 원고·보고를 넘기기 전 |
| 산출물 | 정정된 결과와 문서, 정정 이력, 재발을 막는 메모리·지침·자동 장치 |
| 구성 | 0장 작업 순서, 1~5장 오류 유형별 신호와 대응, 6장 공통 대응. 대응 규칙이 다른 장에 있으면 그 장을 가리킴 |

## 0. 작업 순서
AI 출력에서 이상한 점을 발견했을 때 거치는 순서와 각 단계의 산출물임. 신호를 알아차리면 정정하기 전에 원본과 실행 경로부터 대조하고, 정정한 뒤에는 같은 오류가 다시 나오지 않게 장치 하나로 옮기는 데서 끝냄.

| 단계 | 해당 장 | 산출물 |
| --- | --- | --- |
| 신호 알아차리기 | 1~5장의 "알아차리는 신호" 열 | 의심 항목 목록 |
| 원본 대조 | 6장 | 원본·실행 경로 확인 결과 |
| 정정 | 1~5장의 "대응" 열 | 정정된 결과·문서, 정정 이력 |
| 재발 방지 | 6장 | 메모리·지침·자동 장치 한 개 |

## 1. 판단과 해석의 오류
AI가 결과를 읽거나 방향을 제안할 때 생기는 오류임. 그럴듯한 문장으로 나오므로 근거를 따로 확인하지 않으면 지나치기 쉬움. 대부분 측정한 사실과 추정, 연구자의 결정과 AI의 해석을 섞는 데서 생기므로, 대응은 기록·원본·코드를 다시 확인하고 둘을 나눠 적는 쪽으로 모임. 결과를 판정하거나 방향을 제안하기 전에 이 표의 신호를 대 봄.

| 오류 유형 | 알아차리는 신호 | 대응 |
| --- | --- | --- |
| 초반 흔들림 과대 해석 | 학습 초반 몇 epoch의 평균 차이로 "오른다"고 말함 | 판단 시점을 미리 정하고, 학습이 안정된 뒤의 값으로 판단함 |
| 사전 측정을 진행 근거로 사용 | 학습 없는 측정의 작은 이득을 "될 것"의 근거로 듦 | 멈출 근거로만 씀(03 9.4). 학습 없는 이득은 학습에서 부호가 뒤집히는 일이 반복됨 |
| 닫힌 방향 재제안 | 새 이름으로 이미 시험하고 닫은 방향을 다시 제안함 | 제안 전에 일지·결정 기록·기각 목록을 검색하고, 겹치면 먼저 밝힘(00 원칙 4) |
| 결정 범위 확대 기록 | 연구자가 고른 것보다 넓은 결정을 기록에 적거나, 리더의 해석을 연구자 결정처럼 적음 | 결정은 연구자 원문 그대로 적고, 범위가 애매하면 되물음. 리더가 덧붙인 해석·따름 규칙은 "리더 제안"으로 따로 표시하고, 연구자가 확인하기 전에는 규칙으로 옮기지 않음. 덧붙인 문장이 여러 문서로 퍼지면 출처를 찾을 수 없고, 그 문장을 근거로 다시 제안하게 됨 |
| 근거 없는 설명 | 측정하지 않은 예시를 근거처럼 답함 | 근거를 물으면 기록부터 확인하고, 측정한 것과 추정을 나눠 말함 |
| 논문 서술만 보고 판단 | 선행 방법의 동작을 논문 문장으로만 설명함 | 공개 코드에서 실제 동작을 확인함(02 4.2) |
| 약한 근거의 기대치 | 기대 성능을 단정하고, 다음 질문 하나에 근거가 무너짐 | 기대치는 근거와 함께 추정으로 표시하고, 근거가 약해지면 바로 정정함 |
| 미리 내건 문장에 대고 결과 판정 | 결과가 제안 때 내건 기대 문장과 다르게 나오자 "불리하다"고 보고함 | 논문의 실제 주장, 실험 설정의 기저 비율, 비교 기준(가장 나은 고정 정책)에 대 보고 판정함. 기대 문장은 가설로만 적음 |
| 공정성 규칙의 과한 해석 | 그림 사례 고르기, 검증 뒤 방법 개선, 지표·표 구성 선택, 검증 split 절제 표, 저장된 시험 실행의 재집계를 "사후 조작"·"시험 아님"으로 막거나 원고에 꼬리표를 붙이자고 함. 정리된 지적을 다시 위험으로 꺼냄 | 원인은 규칙의 목적(체리피킹 방지)을 잊고 문구만 적용하는 것임. 막거나 지적하기 전에 00 원칙 5의 목적과 교정 확정 항목(04 4장)에 대 보고, 좋은 값만 골라 숫자를 만드는 일이 아니면 막지 않음 |
| 뒤집힌 결정을 옛 기록대로 따름 | 연구자가 바꾼 결정(제출 범위, 워커 사용, seed 절차 등)과 다른 옛 문장을 메모리·가이드에서 읽고 그대로 따름 | 결정이 뒤집힌 턴에 옛 메모리·가이드 문장을 고치거나 지움(01 4.1). 규칙을 근거로 쓸 때는 그 날짜를 최근 결정과 대조함 |
| 지표 일부만 보고 결론 | 한 지표만 보고 결론을 냄 | 판정 지표 전체로 다시 보고 정정함 |
| 약한 결과를 아이디어 실패로 단정 | 결과가 평평하거나 나쁘면 바로 "효과 없음"으로 정리함 | 03 9.1 순서로 진단함 |
| 특정 기법 쪽으로 치우친 틀 | 모든 제안이 문제보다 특정 기법을 중심으로 쓰임 | 제안을 측정된 문제에서 다시 세우고, 기법은 도구의 자리로만 둠 |
| 기존 구현 오해 | 기준 코드가 이미 하는 일을 새 기여로 제안함 | 제안 전에 해당 코드를 직접 읽음 |
| 조건을 넘는 추론 | 한 조건의 결과를 다른 조건에도 성립한다고 말함 | 다시 재기 전까지 추정으로 표시함 |
| 수치 단위 오류 | 퍼센트포인트와 상대 비율을 섞음 | 숫자는 원본에서 다시 계산하고 단위를 함께 적음 |

## 2. 실험과 코드의 오류
실험을 설계·실행하거나 코드를 고칠 때 생기는 오류임. 결과가 틀려도 숫자는 나오므로, 결과가 이상하면 먼저 실행 경로를 의심함. 다른 하나의 축은 이유 없는 실험과 확인임. 실험·재학습·확인을 제안하기 전에 그 결과가 바꾸는 결정과 이미 있는 결과를 따지고, 대응의 세부는 대부분 03의 해당 절에 있음.

| 오류 유형 | 알아차리는 신호 | 대응 |
| --- | --- | --- |
| 정해 둔 수정안 자동 실행 | 실패한 뒤 진단 없이 미리 정한 수정안을 바로 돌림 | 03 9.1 |
| 이유 없는 실험 제안 | "자원이 비어서" 실험을 제안함 | 기대 이득과 역할을 먼저 밝히고, 없으면 제안하지 않음(00 원칙 10) |
| 이미 있는 값을 얻으려 재학습 | 끝난 실험을 다시 돌리거나, 기록 장치를 새로 넣은 뒤 결과가 있는 기준 줄을 다시 돌림 | 03 8.3 |
| 과한 확인과 증명 | 이미 보인 사실을 다시 재거나, 아무 결정도 바꾸지 않는 확인을 제안함. 연구자가 "이건 왜 또 하나"를 묻게 됨 | 원인은 숨은 차이에 한 번 데인 뒤 위험 없는 곳까지 확인함, 확인 전에 바꾸는 결정을 따지지 않음, 확인이 많으면 신중하다고 착각함의 셋임. 대응은 03 6.3 |
| 한 번에 여러 변경 | 점수가 떨어졌는데 원인을 가를 수 없음 | 한 줄에 한 변경(00 원칙 6) |
| 수정된 사본 기준 검사 | 다른 사람이 고친 파일과 비교해 "일치"로 판정함 | 원본 저장소와 논문 식을 기준으로 함(02 4.2) |
| 채점 경로 버그 | 결과가 우연 수준이거나 출력 분포가 거의 평평함 | 이상하게 나쁜(또는 좋은) 결과는 가중치 로드와 채점 경로를 먼저 점검함. 이런 결과가 원고의 주장으로 들어가기 쉬움 |
| 상태가 빠진 재실행 | 체크포인트로 다시 돈 측정의 손실 크기가 원래와 크게 다름 | 03 8.3. 방법의 내부 상태도 함께 저장함 |
| 새 항이 학습에 걸리지 않음 | 새 파라미터가 초기값에 머물거나, 덧붙인 손실 항이 뒤 코드에 덮여 기울기가 0임 | 03 6.3, 7.1 ④ |
| 일괄 편집으로 내용 손상 | 스크립트 편집 뒤 절이 줄거나 머리말이 깨짐 | 편집 뒤 줄 수·절 제목·머리말과 변경 통계를 확인함 |
| 출력 덮어쓰기 | 출력 경로를 빠뜨려 등록된 결과 파일을 덮음 | 새 폴더에만 쓰고, 등록본은 읽기 전용으로 둠(03 4.3) |
| 표기·ID 버그 | 분류 표기나 내려받기 실패 수가 이상하게 많음 | 사후 보조 진단으로 원인을 확인하고 원장에 남김 |
| 사전 등록에 임의 문턱 | AI가 근거 없는 통과 문턱을 만들어 넣음 | 사전 측정 등록에는 문턱 없이 순위와 서술만 둠 |
| 설계 문서와 다른 값 기재 | 설계 문서의 설정이 실제 학습 설정과 다름 | 설계 값은 코드 설정에서 옮겨 적음 |
| 전제 조건을 빠뜨린 대기열 | 먼저 해야 할 이식·수정 없이 비교 실험을 대기열에 올림 | 올리기 전 계획 문서의 선행 조건을 확인함 |

## 3. 원고와 표의 오류
원고와 표를 다룰 때 생기는 오류임. 자동 숫자 대조가 닿지 않는 곳에서 주로 생김. 체크 표시, 요약 수치, 주장 단어, 그림의 판처럼 숫자 밖의 칸은 결과 보고서·빌드 결과와 사람이 직접 대조함. 원고·표를 넘기기 전에 이 표의 신호를 확인함.

| 오류 유형 | 알아차리는 신호 | 대응 |
| --- | --- | --- |
| 표 칸 뒤바뀜 | 체크 표시나 칸 값이 결과 보고서와 다름 | 독립 검토를 두고, 표마다 보고서와 칸 단위로 대조함. 숫자 자동 대조는 체크 표시를 보지 못함 |
| 출처 없는 요약 수치 | 초록·본문의 수치가 어느 표·그림 칸과도 맞지 않음 | 수치는 실제 칸에서 가져오고 범위를 밝힘 |
| 구간과 어긋난 주장 | 신뢰 구간이 0을 포함하는데 "더 낫다"고 씀 | 06 2장 주장 단어 규칙 |
| 확인 없는 단정 | 빌드·출력을 보지 않고 "이렇게 나온다"고 말함 | 단정 전에 실제 빌드 결과를 확인함 |
| 걸러 읽은 출력의 착시 | 줄을 걸러 읽은 출력(일부 줄만 뽑기, 줄 빼기, 열 자르기)을 보고 "없다·비었다·남는다"고 지적함 | 원인은 보는 방식이 지운 줄을 원고에 없는 것으로 읽는 것임. 그런 지적은 그 범위를 거르지 않은 원문이나 렌더된 출력으로 한 번 더 확인한 뒤 냄(06 2.1) |
| 오해를 부르는 그림·표 | 표시가 한 항목에만 붙어 다른 항목의 조건이 잘못 읽힘 | 조건은 묶음 머리에 표시함 |
| 그림과 캡션의 판 불일치 | 그림만 옛 판으로 남아 캡션과 어긋남 | 05 6장 픽셀 비교 |
| 공을 잘못 돌림 | AI 사용 고지에 AI가 아이디어·설계를 한 것처럼 쓰거나, 우리 부품을 "선행을 따름·채택함"으로 써 공을 선행에 돌림 | 04 4.1, 06 3장 |

## 4. 데이터와 시각 판독의 오류
AI가 영상·데이터를 읽거나 만들 때 생기는 오류임. 사람의 확인이 기준이 됨. AI의 판독·생성물은 그대로 쓰지 않고 사람의 확인이나 표본 검사를 거치며, 시험 데이터에 닿은 출력은 지우고 공개함.

| 오류 유형 | 알아차리는 신호 | 대응 |
| --- | --- | --- |
| 시각 판독 오류 | 사람이 직접 본 것과 AI 판독이 다름 | 사람이 확인한 자료를 기준으로 하고 정정 이력을 남김 |
| 생성된 기록 오류 | 모델이 만든 기록·메모의 상당 부분이 틀림 | 그대로 믿지 않고 표본을 검사함 |
| 생성된 평가 문항 결함 | AI가 만든 평가 문항 중 결함이 섞임 | 평가 중 결함을 발견하면 그 회차를 점수를 열지 않고 폐기함 |
| 시험 정보 노출 | 시험 데이터 정보를 본 출력이 있음 | 출력을 지우고, 한 번 봤다는 사실을 논문에 공개함 |

## 5. 소통과 운영의 오류
대화와 실행 운영에서 생기는 오류임. 대부분 문맥이 길어지거나 요약된 뒤에 다시 나타남. 연구자와의 소통에서는 쉬운 말과 대상 확인이, 실행 운영에서는 실행기 기록 확인이 공통 대응이며, 운영 쪽 세부는 05의 해당 장에 있음.

| 오류 유형 | 알아차리는 신호 | 대응 |

| 용어를 설명 없이 사용 | 연구자가 "그게 무슨 뜻이지?", "쉽게 설명해줘"라고 물음 | 쉬운 말과 구체적인 크기·예시로 설명함. 측정 결과도 "무엇을 쟀고 무엇이 나왔나"를 예시로 먼저 말한 뒤 표를 붙임(00 4.3) |

## 6. 공통 대응
여러 유형에 공통으로 쓰는 대응 원칙임. 정정은 원본 대조를 거쳐 기록으로 남기고, 같은 오류가 반복되면 말이 아니라 장치와 목적 문장으로 막는 것이 핵심임.
- 시각 판독·수치·단위·인용은 AI 출력을 그대로 쓰지 않고, 사람 확인 열이나 원본 대조를 거친 뒤 정정 이력을 남김.
- 결과가 기대와 크게 다르면 방법을 의심하기 전에 실행 경로(채점, 상태, 설정)를 먼저 확인함.
- AI가 틀린 것을 인정하고 정정하면, 정정 내용을 일지에 남겨 다음 세션이 같은 판단을 반복하지 않게 함.

같은 실수가 두 번 나오면 말로 다시 지적하지 않고 메모리·지침·자동 장치 중 하나로 옮김. 기계적으로 판별할 수 있으면 자동 장치를, 판단이 필요하면 지침을 고름. 또한 같은 종류의 정정이 여러 번 나오면 사례 규칙("이것도 괜찮음")을 하나 더하지 않고, 그 규칙이 무엇을 막으려는지 목적을 한 문장으로 적어 둠. 사례만 쌓이면 다음 사례에서 같은 정정이 되풀이됨.
