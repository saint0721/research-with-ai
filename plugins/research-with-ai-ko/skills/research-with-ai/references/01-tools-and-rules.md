# AI 활용 연구 방법 — 도구와 규칙 체계

| 항목 | 내용 |
| --- | --- |
| 목적 | 이 문서만 보고 AI 에이전트와 연구할 도구를 갖추고, 지침·메모리·스킬·훅·위키를 만들어 운영할 수 있게 함 |
| 읽는 상황 | 새 연구나 저장소를 시작할 때, 같은 지시를 반복하게 될 때, 지침·메모리·스킬·훅·위키를 만들거나 고칠 때, 세션이 바뀌어 연구가 끊길 때 |
| 산출물 | 도구 구성, 규칙 계층에 맞춘 지침 파일, 메모리·스킬·훅, 위키 골격(상태 색인·주제 페이지·일지), 문서화 시점표, 감시 설정 |
| 구성 | 0장 작업 순서, 1~8장 방법 |

## 0. 작업 순서
연구 환경을 처음 갖출 때 거치는 단계와 각 단계의 산출물임.

| 단계 | 장 | 산출물 |
| --- | --- | --- |
| 도구 갖추기 | 1 상시 사용 도구, 2 요청 시 사용 도구 | 에이전트·화면·서버·문서 저장소 구성 |
| 규칙 세우기 | 3 규칙 계층, 4 규칙 도구 작성 | 지침 파일, 메모리, 스킬, 훅 |
| 기록 체계 | 5 LLM 위키, 6 문서 체계 | 위키 골격, 문서화 시점표, 문서 형식 |
| 긴 작업 대비 | 7 감시와 모니터 | 감시 명령, 모니터 칸 |
| 계속 개선 | 8 방법 문서의 점진 개선 | 개선 후보 노트, 개선 일지 |

## 1. 상시 사용 도구
일상 연구 작업에 매번 쓰는 도구의 역할과 운용 원칙임.

| 구분 | 도구 | 역할과 운용 원칙 |
| --- | --- | --- |
| 에이전트 | 주 작업 에이전트 | 설계·분석·코드·검증·커밋·문서화를 직접 수행함. 짧은 일은 다른 에이전트에 넘기지 않음. 워커는 지시서와 코드를 읽는 시간이 일보다 길고, 코드만 쓰고 실행하지 않은 채 멈추기도 함 |
| 화면 | 터미널 화면 분할 도구 | 에이전트와 감시 화면을 보이는 칸으로 나눔. 감시 칸은 대화 칸 옆이 아니라 아래에 둠 |
| 계산 | 원격 GPU 서버 | 학습과 측정을 수행함. 에이전트는 노트북에서, 계산은 서버에서 수행하는 구조이며, 학습은 대기열 실행기로 띄움 |
| 문서 | 코드 저장소 문서 | 연구 결정과 숫자의 정본임. 상태 색인·주제 페이지·일지를 둠 |
| 문서 | 노트 저장소 | 사람이 읽는 정리 문서임. 대화 기록을 쌓는 곳이 아님. 프로젝트마다 허브 문서와 전체 자료 인덱스를 둠 |
| 규칙 | 지침 파일 | 에이전트가 작업 시작 시 읽는 규칙임 |
| 규칙 | 메모리 | 사고에서 나온 교훈과 연구자의 결정 원칙을 이유와 함께 보존함 |
| 규칙 | 스킬 | 반복 절차를 묶어 두고 상황이 맞으면 자동으로 불러옴 |
| 규칙 | 훅 | 정해진 시점에 자동으로 실행되는 확인 스크립트임 |
| 결과물 | 브라우저 페이지 | 라벨링 페이지·정성 사례·판독 페이지처럼 브라우저로 보는 결과물에 사용함 |

## 2. 요청 시 사용 도구
여러 에이전트를 묶는 도구는 연구자가 명시적으로 요청할 때만 사용함. 열린 칸이 있거나 병렬 이득이 예상된다는 이유만으로는 사용하지 않음. 비용과 혼선이 커지기 때문이며, 이 제한은 전역 지침에 적어 둠.

| 기능 | 역할 | 사용 조건 |
| --- | --- | --- |
| 상담 | 읽기 전용 상대 에이전트와 여러 턴에 걸쳐 토론함. 상대는 파일을 고치지 않으며, 결론은 판단 근거일 뿐 승인이 아님 | 아이디어·설계를 확정하기 전 검토, 완료한 결과물에 대한 2차 의견 |
| 세션 넘기기 | 현재 상태를 파일 하나로 기록하고, 새 세션이 그 파일을 읽어 작업을 이어받음 | 대화가 길어져 응답이 무거워진 경우, 한 단계가 끝난 경계 |
| 세션 이어받기 | 사용 한도 도달이나 화면 소실로 끊긴 작업을 다른 세션이 이어받음. 과거 대화 기록 검색도 포함함 | 사용 한도 도달, 터미널 종료로 작업이 끊긴 경우 |
| 워커 묶음 | 여러 워커에게 겹치지 않는 일을 나눠 맡기고, 커밋으로 완료를 증명함 | 서로 독립인 작업이 여럿이고 병렬 수행을 요청한 경우 |
| 원격 작업 | 노트북의 워커가 원격 서버에서 작업하게 함 | 서버 작업을 별도 워커에게 맡기는 경우 |
- 상담 도구의 기본 예산은 주고받기 몇 번이면 끝나는 경우가 많으므로, 실제 토론에는 턴 수·시간을 넉넉히 주고 끝낼 때 결론 요약을 남겨 기록으로 씀.
- 세션 넘기기는 진행 중인 파일 작업을 마친 뒤에만 함. 넘김 파일에는 남은 작업·근거 위치·다음 명령을 적고, 새 세션에는 그 파일을 읽으라는 두세 줄 지시만 전달함.

## 3. 규칙 계층
규칙은 적용 범위에 따라 층을 나누며, 각 규칙은 가장 좁은 층에 둠.

| 층 | 담는 규칙 |
| --- | --- |
| 연구자 직접 지시 | 모든 규칙보다 우선함 |
| 전역 지침 | 코딩 자세, 조립식 모델 개발 원칙, 도구 사용 제한 |
| 노트 저장소 지침 | 문체, 파일명, 허브 문서, 판정표 형식 |
| 프로젝트 지침 | 프로젝트 경계, 위키 구조, 문서 층 |
| 코드 저장소 지침 | 빌드·실행 명령, 개발 순서, 측정 규칙 |
| 메모리 | 사고 교훈과 결정 원칙 |
| 스킬 | 반복 절차 |
- 우선순위는 연구자 지시 > 가장 가까운 지침 > 상위 지침 > 전역 지침 순서임.
- 같은 규칙을 사람용 문서와 에이전트용 지침에 함께 두고 함께 고침.

## 4. 규칙 도구 작성 방법
같은 지시를 반복하게 되면 말로 다시 하지 않고 지침·메모리·스킬·훅 중 하나로 옮기는 것이 기본 방향임.

| 도구 | 만드는 시점 | 형식 | 검증 |
| --- | --- | --- | --- |
| 지침 | 같은 지시가 두 번 이상 반복되거나 프로젝트별 규칙이 생긴 시점 | 규칙 한 줄과 이유 한 줄. 긴 설명은 운영 문서로 분리하고 위치만 기재 | 새 세션에서 해당 규칙이 필요한 작업을 시켜 준수 여부 확인 |
| 메모리 | 사고·연구자 정정·연구자 결정이 생긴 시점 | 규칙 하나당 파일 하나, 규칙 → 이유 → 적용 방법 | 같은 상황에서 다시 틀리지 않는지 확인 |
| 스킬 | 같은 절차를 여러 번 설명하게 된 시점 | 폴더 하나와 절차 파일 하나, 길어지면 참고 파일로 분리 | 발동 문구를 말했을 때 스킬을 불러오는지 확인 |
| 훅 | 지침만으로는 지켜지지 않고 기계적 판별이 가능한 규칙이 생긴 시점 | 설정 파일에 등록한 확인 스크립트 | 가짜 입력으로 막아야 할 경우와 통과할 경우를 각각 시험 |

### 4.1 형식
| 도구 | 형식 기준 |
| --- | --- |
| 메모리 | 규칙 하나를 파일 하나에 둠. 앞머리에 이름·한 줄 설명·종류를 두고, 본문은 규칙 → 이유(계기 사건) → 적용 방법 순서로 씀. 색인 파일에는 제목과 한 줄 요약만 둠. 같은 내용이 있으면 새로 만들지 않고 고치며, 틀린 기억은 지움 |
| 스킬 | 앞머리의 `description`이 발동 조건이므로, 기능 설명보다 언제 읽어야 하는지와 실제로 쓰는 표현(한국어 포함)을 담음. 본문이 길어지면 참고 파일로 나누고, 본문에는 상황별로 읽을 파일 표만 둠 |
| 훅 | 출력이 대화 문맥을 차지하므로 평소에는 아무것도 출력하지 않게 만듦. 예: 응답 종료 시점에 "이번 턴에 실행 시작이나 처음 보는 결과가 있었는데 일지를 안 고쳤는가"를 검사해 한 번 막는 훅. 이미 본 결과는 따로 기억해 같은 결과로 다시 막지 않음(없으면 오래된 결과로 반복해서 막히는 오탐이 생김) |

## 5. LLM 위키 활용
에이전트가 직접 쓰고 고치는 주제별 위키로 연구 상태를 한곳에 유지하는 방법임. 날짜별 카드에 판단이 흩어지면 카드마다 숫자가 달라 결정이 흔들리므로, 세션이 바뀌어도 하나의 최신 상태를 이어 쓰는 것이 목적임. 한 프로젝트에서 쓰던 위키 구조는 다른 프로젝트에도 그대로 옮겨 씀. 구조는 Karpathy의 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 패턴을 따름.

### 5.1 구조
| 층 | 내용 | 작성 주체 |
| --- | --- | --- |
| 원천 | 날짜 카드와 결과 문서. 위키 작업 중에는 읽기만 함 | 사람·에이전트(새 문서 추가만) |
| 위키 | 날짜 없는 주제 페이지. 덮어써서 늘 최신으로 유지함 | 에이전트 |
| 스키마 | 프로젝트 지침의 위키 규칙 | 연구자와 함께 고침 |
- 위키 안에는 상태 색인 한 장(40줄 안팎), 주제 페이지 여러 장, 일지 하나가 있음. 계속 쌓이는 문서는 일지뿐이며, 색인과 주제 페이지는 덮어씀.
- 주제 페이지는 현재 상태 → 구성 → 측정값 → 결정 → 미해결·이견 → 대체된 판단 순서이며, 150줄을 넘으면 오래된 내용을 보관 문서로 옮김.
- 항목에는 `[확정]`·`[추정]`·`[미확인]` 표지를 붙이고 신뢰도 점수는 쓰지 않음.
- 일지는 사건 하나에 한 항목이며, 연구자 원문 인용과 무엇을 고쳤는지를 적음.

### 5.2 위키를 쓰는 이유
| 효과 | 내용 |
| --- | --- |
| 세션이 바뀌어도 끊기지 않음 | 새 세션이나 문맥 요약 뒤에도 에이전트가 색인과 주제 페이지를 읽으면 현재 상태·결정·다음 할 일을 바로 앎. 지난 대화를 다시 설명할 필요가 없음 |
| 말을 잘 알아들음 | 프로젝트 용어·줄 이름·결정의 뜻이 페이지에 정의되어 있어, 짧게 말해도 에이전트가 같은 뜻으로 이해함 |
| 놓치는 것이 줄어듦 | 결정·제약·닫힌 방향이 한곳에 있어, 닫힌 방향을 다시 제안하거나 제약을 어기는 일이 줄어듦 |
| 숫자가 하나로 맞음 | 같은 사실을 여러 카드에 다르게 적는 문제가 사라지고, 판단이 바뀌면 "대체된 판단"으로 남아 이력이 보임 |

### 5.3 운영 방법
| 동작 | 시점 | 하는 일 |
| --- | --- | --- |
| 읽기 | 세션 시작, 새 제안 전 | 색인 → 관련 주제 페이지 → 일지 최근 항목 순서로 읽음 |
| 질의 | 연구자가 상태를 물을 때 | 위키로 답하고, 숫자는 원천 문서에서 확인함 |
| 반영 | 결과·결정·정정·이해를 바꾼 설명이 생긴 턴 | 같은 턴 안에 일지 한 줄, 주제 페이지 덮어쓰기, 색인 갱신 |
| 점검 | 연구자가 요청할 때 | 반영되지 않은 원천, 근거 없는 주장, 오래된 상태를 찾음 |
| 정리 | 조건(바탕·프로토콜·split)이 바뀌었을 때, 일지가 길어졌을 때 | 옛 조건의 결과·설계·작업 사양과 다 쓴 인계를 날짜 붙은 보관 폴더로 같은 하위 경로째 옮기고, 지금 문서의 링크를 보관 경로로 고침. 주제 페이지와 색인은 지금 조건의 내용만 남기고 정리 전 사본을 보관함. 선행연구·규칙 문서는 조건과 무관해 남김 |
- 위키 갱신은 자동 스크립트가 아니라 지침으로 운용함. 작업을 끝내기 전에 저장소 변경 목록에서 새로 생긴 문서를 확인해 위키에 반영함. 자동 갱신은 검토 없이 페이지를 바꾸기 때문임.
- 반영을 빠뜨리지 않도록 응답 종료 시점의 확인 훅이 "결과가 있었는데 일지를 안 고쳤는가"를 검사함(4.1 훅).
- 위키는 내부 문서이며, 외부 문서는 원천 문서를 근거로 씀.
- 옛 조건의 문서가 지금 폴더에 섞여 있으면 에이전트와 연구자 모두 옛 숫자·닫힘을 지금 근거로 잘못 읽음. 조건이 바뀐 턴 뒤 첫 정리 때 옮김.

### 5.4 노트 저장소와 위키 연결
코드 저장소의 위키와 연구자의 노트 저장소(예: Obsidian vault)를 함께 쓸 때의 역할 분담과 연결 방법임. 둘 다 연구 상태를 적다 보면 숫자와 결정이 두 곳에서 따로 바뀌므로, 정본을 하나로 정하고 다른 쪽은 그것을 가리키게 함.

| 구분 | 코드 저장소 위키 | 노트 저장소 |
| --- | --- | --- |
| 역할 | 연구 상태·결정·숫자의 정본 | 사람이 다시 읽는 정리 문서, 설명, 발표·보고 초안, 방법 문서 초안 |
| 쓰는 주체 | 에이전트가 같은 턴에 덮어씀 | 연구자가 요청하거나 한 단계가 끝났을 때 에이전트가 정리함 |
| 단위 | 상태 색인·주제 페이지·일지 | 프로젝트 폴더마다 허브 문서 하나와 날짜 노트 |
| 지침 | 프로젝트 지침의 위키 규칙 | 노트 저장소 최상위 지침 파일(문체·파일명·허브 규칙)과 폴더별 지침 파일 |
- 노트는 위키 숫자를 옮겨 적지 않고 결과 문서·주제 페이지를 출처로 가리킴. 노트에 숫자를 적어야 하면 출처와 기준 시각을 함께 적음.
- 노트에서 연구자가 결정을 바꾸거나 정정하면 같은 턴에 위키 일지와 해당 주제 페이지에 반영함. 노트만 고치면 다음 세션의 에이전트는 바뀐 결정을 모름.
- 에이전트는 노트를 쓰기 전에 노트 저장소의 지침 파일과 해당 폴더의 지침 파일을 먼저 읽음. 지침은 노트 저장소 쪽에 두고 프로젝트 지침에는 위치만 적음.
- 허브 문서 끝에는 폴더 전체 자료 인덱스를 두어 새 노트가 자동으로 목록에 오르게 함. 노트를 새로 만들 때마다 허브를 손으로 고치지 않아도 됨.
- 노트 저장소는 대화 기록을 쌓는 곳이 아님. 대화에서 정해진 것은 위키 일지에, 다시 읽을 가치가 있는 정리만 노트에 둠.
- 스크립트로 노트를 고친 뒤에는 머리말을 확인함(6.2).
- 문서 없는 코드 변경과, 원천 문서·원천 노트·위키·노트 저장소 사이의 반영 누락은 이 스킬의 플러그인에 든 응답 종료 훅이 잡음(4.1 훅 형식). 지침만으로는 원천 노트에 절을 더하고 위키 반영을 건너뛰는 일이 생기고, 이런 누락은 다음 세션이 틀린 상태를 읽게 만들기 때문임. 훅은 네 가지를 기계적으로 봄.
  1. 문서가 필요한 경로(코드·원고 등)를 바꾼 커밋에 문서가 없음.
  2. 위키가 반영해야 할 원천 문서를 바꾼 커밋 뒤로 위키 일지를 고친 커밋이 없음.
  3. 원천 노트를 바꾼 커밋 뒤로 위키 일지를 고친 커밋이 없음(노트가 위키 작업 사본에 있고 코드 저장소와 다를 때).
  4. 노트 저장소로 보내는 위키 작업 사본에 커밋하지 않은 변경이 있거나, 마지막 반영 표시가 최신 커밋이 아님.
  - 문제가 없으면 아무것도 출력하지 않고, 같은 커밋·상태로는 한 번만, 무엇이 빠졌는지만 한 줄로 알림. 노트 저장소가 다른 기계에 있을 수 있으므로 원격에 접속하지 않고 작업 사본과 반영 표시만 봄.
  - 훅에는 경로가 없음. 각 프로젝트가 `.claude/research-with-ai.conf` 에 자기 값(문서가 필요한 경로, 문서 경로, 위키 저장소 위치, 원천 문서·노트 경로, 위키 일지 파일, 반영 표시, 살펴볼 기간)을 적고, 값을 적은 확인만 돌아감. 파일이 없는 프로젝트에서는 아무것도 하지 않음. 위키가 코드 저장소 안에 있으면 위키 저장소 위치를 `.` 로 둠.
  - 설정 파일은 프로젝트 폴더마다 둠. 훅은 세션을 띄운 폴더의 파일과, 그 아래 세 단계 안 프로젝트 폴더의 파일을 모두 찾아 프로젝트마다 따로 검사함. 그래서 노트 저장소 하나에 프로젝트 위키가 여럿이어도 저장소 루트에서 띄운 세션이 모두 확인함. 파일 안 경로는 그 파일이 든 프로젝트 폴더 기준이고, 알림 앞에 `[프로젝트 경로]` 를 붙임.

## 6. 문서 체계
무엇이 일어났을 때 어디에 기록하는지와 문서의 형식임.

### 6.1 문서화 시점
| 사건 | 일지 | 결과 문서 | 주제 페이지 | 상태 색인 |
| --- | --- | --- | --- | --- |
| 학습 결과 | O | O | O | O |
| 사전 측정·smoke 결과 | O | O | 해당 시 | 상태 변경 시 |
| 연구자 결정·정정 | O | — | 해당 페이지 | 상태 변경 시 |
| 실행 시작 | O | — | 진행 중 표시 | O |
| 이해를 바꾼 설명 | O | — | 쉬운 말 설명 절 | — |
| 실험 조건 결정(바탕 방법·프로토콜·split·예산·이전 모듈을 가져갈지) | O | 계획 문서(확인할 것과 통과 기준을 결과 전에) | 규칙 페이지 | O |
- 단순 상태 확인은 기록 대상이 아님.
- 실험 조건이 바뀌면 이전 조건의 숫자를 새 조건으로 옮기지 않음. 예전 숫자가 섞이면 새 사다리의 판정이 이전 조건 기준으로 흔들림.
- 시각은 짐작하지 않고 시계에서 읽음. 짐작한 시각은 한꺼번에 틀리고, 나중에 기록 전체를 의심하게 만듦.

### 6.2 문서 형식
- 문체는 설명식 개조체(`~임/~필요/~기준/~방향`)이며 대화체는 쓰지 않음. 보고서처럼 읽히는 것이 기준임.
- 노트 파일명은 `YYYY-MM-DD 주제.md`, 허브만 고정 접두어를 쓰며, 허브 끝에는 폴더 전체 자료 인덱스를 둠.
- 판정표는 판정 규칙 → 검증 표 → 관찰 전용 지표 → 최종 판정 순서이며, 에이전트 결함(FAIL)과 외부 조건(BLOCKED)을 구분함.
- 연구자가 읽는 문서에는 따로 찾아봐야 뜻을 아는 코드(결정 번호·측정 코드)와 판 표시(초판·보강)를 쓰지 않음. 연구자는 코드를 봐도 뜻을 알 수 없음.
- 스크립트로 여러 파일을 일괄 수정한 뒤에는 머리말(frontmatter)을 반드시 확인함. 치환 한 번이 머리말의 공백 하나를 지워 여러 문서의 태그를 한꺼번에 깨뜨릴 수 있음.

## 7. 감시와 모니터 운용
긴 작업의 종료를 알리는 감시와, 사람이 진행 상황을 보는 모니터를 구분해 운용함.

| 구분 | 방식 | 기준 |
| --- | --- | --- |
| 감시 | 배경 명령이 종료 표시 줄을 일정 간격(예: 10분)으로 확인하고, 나타나면 에이전트를 다시 깨움 | 짧은 간격의 반복 조회는 하지 않음 |
| 모니터 | 대화 칸 아래 칸 하나에 짧은 진행 상황만 표시함 | 작업당 칸 하나를 재사용함 |
- 프로세스 이름으로 찾으면 감시 명령 자신이 검색되어 감시가 끝나지 않고, 다음 작업 시작이 그만큼 늦어짐. 종료 판단은 프로세스 번호나 로그의 종료 표시로 함.
- 긴 작업을 일반 백그라운드로 띄우면 셸 종료 시 함께 종료되므로 세션에서 분리해 실행함.
- 종료 표시가 없으면 "미확인"으로 보고하며, 성공으로 간주하지 않음.

## 8. 방법 문서의 점진 개선
연구자가 "고쳐라"라고 따로 말하지 않아도, 작업 중에 생긴 교훈이 방법 문서(지침·스킬)에 쌓이게 하는 방법임(점진적 자가발전). 연구자의 정정은 그 턴에 반영되고, AI가 알아낸 교훈은 후보로 쌓여 매듭에서 승인되며, 승인된 변경은 공개판으로 올라가 다음 세션의 스킬이 됨. 훅이 이 고리를 잊지 않게 받침. 코드 없이 문서와 지침만으로 운영함. [LLM 위키](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)의 일지·정기 점검과, 지침을 통째로 다시 쓰지 않고 항목 단위로 고치는 방식([ACE, Agentic Context Engineering](https://arxiv.org/abs/2510.04618))을 따름.

### 8.1 문서만으로 하는 구조
| 문서 | 역할 |
| --- | --- |
| 개선 후보 노트 | 작업 중 생긴 교훈 후보를 한 줄씩 쌓는 곳. 쌓이기만 하고, 반영한 줄에는 반영 표시를 함 |
| 방법 문서(00~06) | 반영 대상. 스킬의 원본이자 설치된 스킬 그 자체 |
| 폴더 지침과 템플릿 | 후보를 어떻게 남기고 어떻게 반영하는지 정한 규칙 |
| 개선 일지 | 언제 어떤 후보를 어느 문서에 반영했는지 한 줄씩 남김 |
- 혼자 쓸 때는 방법 문서 폴더를 스킬 폴더로 그대로 연결할 수 있음(본문 = 스킬 본문, 장별 문서 = 참고 파일). 문서를 고치면 스킬도 바로 바뀌므로 변환·설치 단계가 필요 없음. 이를 위해 문서 사이의 링크는 표준 마크다운 링크로 씀.
- 공개된 스킬을 설치해 쓰면서 그 스킬에 기여할 때는 8.4의 순서를 따름.

### 8.2 운영 순서
1. **연구자가 정한 것은 바로 반영**: 연구자가 정정하거나 새 작업 방식을 정한 턴에는, 그 턴 안에 해당 문서·장을 고치고 개선 일지에 한 줄을 남김. 연구자의 말이 곧 결정이므로 기다리지 않음. 나중에 고치면 그 사이의 세션은 고치기 전 규칙으로 일하게 됨.
2. **반영할 곳 고르기**: 모든 단계에 공통이면 본문(00), 한 단계 안의 방법이면 해당 장별 문서, 한 연구에만 해당하면 그 연구 저장소의 지침에 넣음.
3. **반영 방식**: 해당 장에 규칙 한 줄을 더하거나 기존 문장을 고침. 같은 규칙이 이미 있으면 그 문장을 고치고 새로 더하지 않음. 통째로 다시 쓰지 않음.
4. **AI가 알아낸 것은 후보로, 시키지 않아도**: 연구자가 정하지 않은 교훈은 신호가 보인 턴에 후보 노트에 `날짜 / 신호 / 일반화한 교훈 / 대상 문서·장 / 변경 종류`로 한 줄 남김. 신호는 정정이나 빈틈을 드러낸 물음, 같은 실수의 두 번째, 작업 중 새로 만든 절차, 도구·경로 실패와 우회, 연구자의 답답함. 교훈은 범용으로 씀(신호 칸에만 사례, 교훈 칸은 프로젝트·도구 이름·숫자 없이 "언제 → 무엇을 → 왜"; 다른 연구에서도 행동을 바꾸지 않으면 그 연구 저장소 지침으로). 같은 교훈이 있으면 그 줄에 신호만 덧붙임. 일의 매듭에서 쌓인 후보를 모아 한 번에 묻고, 받아들이면 1번처럼 바로 반영, 거절하면 기각 표시.
5. **기록**: 반영할 때마다 개선 일지에 `날짜 / 바꾼 내용 / 고친 문서·장 / 계기(연구자 결정·후보 승인)`를 남기고, 문서 저장소가 git이면 커밋해 되돌릴 수 있게 함.
6. **점검**: 정기적으로(예: 주 1회) 모순, 중복, 너무 길어진 장을 찾아 보고하고, 정리는 승인 뒤에 함.
7. **훅으로 받침**: 지침만으로는 4번을 잊으므로 두 시점에 훅을 둠. 연구자의 말이 정정·빈틈을 드러내는 물음으로 보이면 그 턴의 문맥에 "후보를 남길지" 한 줄을 넣고, 응답이 끝날 때 대기 후보와 공개판 이후 쌓인 반영을 상태마다 한 번씩 알림(4.1 훅 형식: 평소에는 출력 없음, 같은 상태로 다시 알리지 않음). 신호로 볼 말은 설정으로 바꿀 수 있게 하고, 질문형 말끝("~아니야?")처럼 정정이 아닌 꼴로 막히지 않는지 가짜 입력으로 시험함.

### 8.3 지킬 것
- 통째 재작성은 하지 않음. 짧게 줄이다 보면 세부 규칙이 사라짐.
- 한 번의 일로 원칙을 만들지 않음. 같은 교훈이 두 번 이상 나오거나 효과가 확인된 것만 공통 원칙으로 올림.
- 공유할 문서이므로 반영 전에 이름·숫자·경로가 섞이지 않았는지 확인함.
- 후보가 없으면 정리를 하지 않음.

### 8.4 노트에서 다듬고 공개 스킬로 올리기
공개 스킬의 기여자가 자기 노트 저장소에서 방법 문서를 다듬고, 충분히 다듬어진 것만 공개 스킬로 올리는 방법임. 연구 중 교정은 바로 노트에 반영하되, 설치된 스킬과 다른 사용자에게는 검토를 거친 판만 가게 하는 것이 목적임.

| 단계 | 하는 일 | 기준 |
| --- | --- | --- |
| 노트에서 다듬기 | 8.2 순서대로 교정·후보 반영을 노트의 방법 문서에 바로 함 | 반영 전까지는 고친 노트가 설치본보다 우선함 |
| 올릴 판 고르기 | 개선 일지에서 지난번 올린 뒤의 변경을 모아, 문장이 정리되고 다른 장과 어긋나지 않는지 봄 | 연구자가 다듬어졌다고 판단한 것만 올림. 에이전트는 변경이 쌓이면 올릴지 한 줄로 물을 수 있음 |
| 공개 저장소로 옮기기 | 노트 전용 머리말과 노트 링크를 빼고 저장소 파일 이름으로 옮김. 다른 언어판이 있으면 바뀐 문서만 다시 옮김 | 이름·숫자·경로·계정·비밀 값이 없는지 검색함 |
| 확인 | 스킬 검사기와 플러그인 검사로 형식을 확인하고, 버전을 올림 | 검사 통과 |
| 올리기 | 커밋한 뒤 연구자 허락을 받아 push함 | 허락 없이 push하지 않음 |
| 설치본 갱신 | 설치한 도구마다 스킬을 다시 받음(플러그인 갱신, 복사 설치는 다시 복사) | 새 세션에서 스킬이 새 판으로 불리는지 확인함 |
- 올리는 단위는 일지 몇 줄을 묶은 판이며, 교정 한 줄마다 올리지 않음. 잦은 판 변경은 사용자에게 검토되지 않은 규칙을 퍼뜨림.
- 노트에만 있는 연구 고유 내용(사례·숫자·경로)은 올리기 전에 일반 규칙으로 바꾸거나 뺌.
