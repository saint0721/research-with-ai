# AI 활용 연구 방법 — 실행 운영

| 항목 | 내용 |
| --- | --- |
| 목적 | 이 문서만 보고 AI 에이전트와 함께 에이전트·서버·GPU·감시·비용·보안·커밋을 운영할 수 있게 함 |
| 읽는 상황 | 워커나 조사 에이전트를 띄울 때, 서버에서 긴 작업·학습을 띄우고 감시할 때, 유료 API나 비밀 값을 다룰 때, 커밋·push할 때 |
| 산출물 | 띄운 작업의 인계 정보(프로세스 번호·로그·예상 종료 시각), 감시 명령, 비용 계산, 정리된 커밋 |
| 구성 | 0장 작업 순서, 1~6장 방법. 분야와 무관한 방법이며 그대로 지침·스킬로 옮길 수 있는 형태임 |

## 0. 작업 순서
작업 하나를 맡기고 띄우고 끝을 확인해 기록하기까지 거치는 장과 산출물임.

| 순서 | 장 | 산출물 |
| --- | --- | --- |
| 맡기기 | 1 리더와 워커의 역할 | 누가 할지, 워커 지시서 |
| 띄우기 | 2 긴 작업 규칙, 3 서버와 GPU | 추정 시간, 띄운 작업의 인계 정보 |
| 기다리기 | 4 감시와 모니터 | 감시 명령 하나, 모니터 칸 |
| 지키기 | 5 보안과 비용 | 비용 계산, 비밀 값 필터 |
| 남기기 | 6 커밋과 push | 커밋, 승인 뒤 push |

## 1. 리더와 워커의 역할
에이전트 여럿을 쓸 때 누가 무엇을 하는지 정하는 방법임. 워커를 늘리는 것보다 리더가 직접 끝내는 편이 빠르고 싼 경우가 많음.

- 사전 측정 스크립트와 작은 코드 변경은 리더가 직접 쓰고 돌림. 워커가 지시서와 코드를 읽고 환경을 맞추는 시간이 실제 계산보다 훨씬 긴 경우가 많고, 워커가 코드만 쓰고 실행하지 않은 채 멈추는 일도 생김.
- 워커는 연구자가 요청할 때만 띄움. 쓸 때는 한 워커에 한 질문·한 파일 범위만 맡기고, 여러 워커의 결과를 하나의 문서로 종합하는 일은 리더가 함. 짧은 문서 작업에는 워커를 쓰지 않음.
- 조사는 좁은 질문 여러 개로 나눠 조사 에이전트를 병렬로 띄우고, 본문 확인 수준을 표시하게 함.
- 서로 독립인 단계는 GPU를 나눠 동시에 돌림. 한 GPU에 순서대로 묶지 않음. 단계를 나누고 겹쳐 돌리면 결정에서 학습 시작까지의 시간이 크게 줄어듦.
- 통과선이 없는 사전 측정은 학습을 막지 않음. 학습을 먼저 띄우고 측정은 다른 GPU에서 함께 돌리며, 해가 나오면 그때 학습을 멈춤.
- 실행기가 학습 전에 smoke를 돌리면, 워커가 같은 smoke를 따로 돌리지 않음.
- 에이전트는 마지막 감시 하나만 두고 한 번만 깨어나게 하며, 커밋한 뒤에는 멈춤. 에이전트를 계속 돌려 두면 토큰 비용이 빠르게 늘어남.
- 워커는 따로 떨어진 작업 공간(worktree)에서 커밋만 하고, 합치기와 충돌 해결은 리더가 함. 작업 줄이 옛 main에서 갈라졌으면 main 구조 위에 작업 줄의 값만 옮김.
- 워커가 쓴 코드는 리더가 설계 문서와 한 줄씩 대조해 분석·검토하고, 시험·smoke·학습은 리더가 직접 돌림. 워커의 "시험 통과" 보고만으로 학습하지 않음(워커 시험이 겨냥한 성질을 실제로 가르는지도 봄 — 예: 같은 seed로 만든 두 모델을 비교하는 시험은 거의 늘 통과함).
- 워커 지시서에는 맡긴 범위 밖의 작업 환경(접속·인증 설정, 시스템 설치, 다른 실험의 파일, 열린 앱)을 바꾸지 말라고 적고, 서버나 외부 자원에 닿지 않으면 고치려 하지 말고 멈춰서 보고하라고 적음. 막힌 워커는 스스로 우회로를 찾다가 연구자의 작업 환경을 바꿀 수 있음.
- 워커 지시서에는 질문 창을 띄우지 말라고 적음. 모르면 안전한 기본값을 쓰고 인계 기록에 적게 함.
- 검증·자문 워커와 실행 워커는 다른 모델 계열을 써서 검증의 독립성을 지킴. 모델 이름은 코드에 박지 않고 설정으로 고름.
- 사용 한도에 걸리면 미리 정해 둔 저가·무료 경로로 바꾸고, 정책 사본을 그대로 씀.
- 다중 에이전트 도구의 성능은 메시지 수나 확인 응답 수로 판단하지 않음. 판단 지표는 완료한 과업당 비용과 결과의 질이며, 평가자가 과업 정보를 미리 보면 그 평가는 무효로 처리함. 같은 접두 문맥을 재사용하고 도구 출력을 줄이면 비용이 크게 줄어듦.
- 작은 코드 변경을 리더와 워커 중 누가 맡을지 지시가 엇갈리면, 연구자에게 한 번 묻고 그 답을 운영 문서에 적음.

## 2. 긴 작업 규칙
10분이 넘을 수 있는 작업(전처리, 평가, 사전 측정)을 돌릴 때 지시서에 그대로 붙이는 규칙임.

1. **먼저 추정함.** smoke에서 표본당 시간을 모델 계산·CPU 작업·채점으로 나눠 재고, 전체 예상 시간을 보고함. 45분이 넘으면 병목과 고친 방법을 적음. 모델 준비 같은 시작 비용은 표본당 시간에서 빼고 추정함.
2. **비어 있는 CPU 코어를 처음부터 씀.** 표본별 CPU 작업은 데이터 로더 worker나 프로세스 풀에서, 무거운 채점은 GPU에서 함. 계산은 빠른데 한 코어에서 채점하느라 전체가 몇 배 느려지는 일이 흔함.
3. **처리 속도를 한 번 점검함.** 전체의 약 5%가 지난 뒤 GPU 사용률과 가장 바쁜 코어를 잼. GPU가 놀고 한 코어만 바쁘면 멈추고 고쳐 다시 돌림. 다만 스크립트가 이 점검으로 스스로 멈추게 하지 않고 숫자만 보고함. 공유 저장소에서 읽는 시간이 병목인 작업은 GPU 사용률이 원래 낮음.
4. **중간 결과를 저장함.** 일정 간격으로 저장하고 이어서 돌 수 있게 함. 출력 단계는 저장된 값만 읽게 해, 마지막 단계에서 죽어도 몇 초 만에 다시 냄.
5. **smoke는 모든 분기를 지나게 함.** 실제 출력 단계까지 돌고, 데이터에 따라 갈리는 모든 분기를 한 번씩 지나게 함. smoke가 지나지 않은 분기는 긴 실행의 마지막에서 터질 수 있음.
6. **실제 시간을 함께 적음.** 보고에는 추정 시간 옆에 실제 시간을 적음.
7. **띄우면 바로 인계함.** 작업을 띄운 뒤 기다리지 않음. 프로세스 번호, 로그 위치, 출력 위치, 예상 종료 시각을 넘기고 끝냄. 기다리기는 리더의 감시 하나가 맡고, 긴 sleep을 한 번에 걸지 않음. 긴 sleep은 결과를 늦게 알아채게 함.

## 3. 서버와 GPU
원격 계산 서버를 쓰는 방법임. 에이전트는 노트북에서, 계산은 서버에서 하는 구조를 전제로 함.

- 긴 작업은 셸과 분리해 띄움(`setsid nohup … &`). 그냥 백그라운드로 띄우면 접속이 끊길 때 함께 죽음. 실행 권한이 없는 스크립트는 `bash`를 앞에 붙임.
- 띄우는 순서와 명령을 운영 문서에 그대로 등록해, 매번 다시 헷갈리지 않게 함. 실행기의 인자 형식도 함께 적음.
- 띄운 뒤에는 대기열 기록의 시작 줄을 확인하고, 실제 학습 시작 줄을 본 뒤에만 "학습 시작"으로 보고함.
- 프로세스는 번호로만 멈춤. 이름 패턴으로 죽이면 명령 자신이나 남의 작업이 함께 죽음.
- 다른 사람이 쓰는 GPU는 쓰지 않음. 허락받은 GPU만, 정해진 시간대에만 씀. 시간 제한이 있는 GPU는 실행기가 시간 밖 시작을 거부하고, 마감 전에 끝나도록 함.
- 공유 저장소의 응답이 느려지는 시간대가 있으면 그 시간대에는 새 작업을 시작하지 않음. 그 시간대의 시험 실패는 코드 탓으로 보지 않음. 예외 스위치를 둬 연구자가 허락하면 건너뜀.
- 새 도구를 설치하기 전에 이미 서버나 공유 저장소에 있는지 확인함. 설치는 개인 가상환경에만 함.
- 원격 셸의 환경이 다르면(예: 가상환경이 켜지지 않음) 실행 파일 경로를 명시함.
- 큰 원본은 스트리밍으로 읽고 필요한 결과(예: 임베딩)만 남김. 긴 대화형 작업은 터미널 다중화 도구 안에서 돌림.
- 사전 측정은 빈 GPU에서 메모리 상한과 낮은 우선순위로 돌림.
- GPU를 꽉 쓰는 방법: 다음 입력을 CPU가 미리 준비하고, GPU를 다 못 쓰는 작은 작업은 메모리가 남는 GPU에 두 번째 자리로 넣음. 학습은 두 번째 자리에 넣지 않음. 처음 돌리는 종류는 혼자 돌려 최대 메모리를 잰 뒤에 넣음.
- 진행 중인 실험에서는 batch 같은 실행 설정을 바꾸지 않음. 숫자가 바뀔 수 있음.
- 서버 공백에 대비해 결과를 백업하고, 백업만 하지 말고 복원 시험도 함.

## 4. 감시와 모니터
긴 작업이 끝났는지 알아채는 방법과 흔한 실수임.

- 끝 확인은 로그의 끝 표시 줄(종료 줄, smoke 결과 줄, 첫 epoch 줄)로 함. 프로세스 이름 검색은 감시 명령 자신과 일치해 영원히 "실행 중"으로 보일 수 있으므로, 쓰려면 자기와 맞지 않는 꼴(`[s]moke`)로 씀.
- 끝 표시를 찾을 때는 이번 실행의 줄만 맞도록 패턴을 정함. 지난 실행의 실패·건너뜀 줄이 남아 있으면 감시가 바로 끝난 것으로 오판함.
- 감시 출력은 grep으로 확인함. 셸마다 단어 분리 규칙이 달라 변수로 나누면 오판하고, 그동안 GPU가 놀 수 있음.
- 노트북을 옮기거나 절전하면 로컬 감시와 VPN이 끊기고 알림이 늦게 옴. 연구자가 돌아와 물으면 감시 출력이 아니라 서버의 대기열 기록부터 확인함. 네트워크 설정은 에이전트가 건드리지 않고 사람이 다시 연결함.
- 실행을 멈추면 그 실행을 기다리던 감시도 함께 멈춤. 끝나지 않을 감시를 남기지 않음.
- 사람이 보는 모니터는 대화 칸 아래에 한 칸으로 두고 짧은 출력만 보여 줌.
- 긴 로그는 tail로 보지 않고 원격 grep으로 필요한 줄만 뽑음. 줄이 긴 로그는 tail 창이 결과 줄을 놓침.

## 5. 보안과 비용
개인정보·비밀 값·외부 반출·유료 API를 다루는 규칙임.

- 사용자 이메일 같은 개인정보를 명령·API 인자·파일에 넣지 않음. 일부 검색 API는 연락처를 요청 인자로 받으므로 조사 에이전트 지시문에 금지 문장을 넣음.
- 비밀 값이 들어 있을 수 있는 줄(예: 옛 로그의 webhook 주소)은 출력하지 않도록 필터를 붙이고, 관련 환경변수는 빈 값으로 실행함.
- VPN·네트워크 설정은 건드리지 않음. 끄라는 지시가 있을 때 정해진 정지 스크립트만 실행함.
- API 키는 사람별 프로파일로 나누고, 기록에는 금액만 남기고 키 값은 남기지 않음. 한 실행에는 키 하나만 씀. 여러 키를 합쳐 한 실행을 나누면 기록과 재시도가 갈라짐.
- 유료 API는 크레딧 만료일을 보고 먼저 쓸 키를 정하고, 실행 전에 실측 단가로 비용을 계산해 잔액 안인지 확인함. 같은 모델·문장으로 이미 실측했으면 파일럿 생략 사유를 사전 등록 문서에 적음.
- 용역·과제의 보안 조건은 설계 요구사항으로 바로 옮김. 예: 외부 반출 금지 → 로컬에서 도는 모델, 암호화 보관, 파기 확인. 원본 보존 여부는 연구자가 정함.

## 6. 커밋과 push
코드·문서·원고의 변경을 기록하고 내보내는 규칙임.

- 의도한 파일만 커밋함. 디렉터리 단위로 추가하지 않고, 남이 고치던 미커밋 파일은 건드리지 않음.
- push는 사람이 지시했을 때만 하고, push 전에 비밀 값 점검을 함. 정해진 원격 브랜치에만 올리고, 공유 저장소의 다른 브랜치나 main을 건드리지 않음. 연구자 혼자 쓰는 저장소는 작업 브랜치가 main에서 곧게 이어질 때(fast-forward) main에도 올림. main을 강제로 덮어쓰지 않음.
- push 전 문서 점검: 변경에 대응하는 계획·결과·설계 문서가 갱신됐는가, 머리말이 있는가, 실패·누락이 기록됐는가, 문서가 가리키는 경로가 실제로 있는가, 남은 작업이 의도된 것인가, 결과 데이터가 커밋에 섞이지 않았는가, 무엇을 왜 올리는지 한 줄 요약이 있는가.
- 결과 데이터는 git에 넣지 않고 별도 저장소(예: NAS)에 둠.
- 원고도 git으로 추적하고, 빌드 산출물과 옛 백업은 제외함. 비공개 저장소일 때만 원고를 push함.
- 사전 등록 문서는 결과 전에 커밋해 시각을 남김. 시각은 짐작하지 않고 시계나 커밋 시각에서 읽음.
